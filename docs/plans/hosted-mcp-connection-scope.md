**In short, a hosted MCP server is a second tool source for the grants plan's §10, not a new connector.** It adds one new `Integration.type`, `hosted-mcp`, a per-person Connection (§10.1). Its tools come from a catalogue entry this repo pins, not from the hand-written map in `toolBrokerService.ts`. A member connects their own account through the vendor's authorization server. ## 1. What kind of row this is

The grants plan's two questions from §10.0, in order:

1. **What does the row do?** An agent acts at an outside service through it, so it is a **Connection**: it lives on the Tools page, and pieces 1–5 apply. It is never a channel, because a hosted MCP server answers calls and carries no pod's messages.
2. **Whose account does the provider see?** The member's. `hosted-mcp` ships in **member mode only**: one row per person per entry, owned by `createdBy`, and that person is its only granter.

Vendors do offer an app identity on these same servers. Linear's bearer path lets a client "interact with the MCP server as an app user", and GitHub's server takes installation tokens to "operate as the application itself" (`docs/policies-and-governance.md` in GitHub's MCP server repository). An app mode is therefore possible later. It would be an App row (§10.2 path 2) with its own type, as `github-app` is, not a mode flag on this one. §10.0 makes `type` the only fact that tells an App row from a per-person row, so one type holding both would leave question 2 without an answer.

## 2. The record

```ts
{ type: 'hosted-mcp',
  scope: 'user', createdBy: <the person>, status: 'pending' | 'connected' | 'disconnected' | 'error',
  config: {
    entryId: 'linear',              // which catalogue entry (§3); fixed at the first connect
    intake: 'oauth',                // the only intake for this type
    providerSubject,                // the provider's stable id for the account, when the AS or the entry's subject read gives one (§4)
    providerSubjectSource,          // 'id_token' or 'tool': where providerSubject came from (§4)
    grantedScope: 'read openid',    // the token response's `scope`, what the person consented to
    clientId,                       // the client that minted the pair: a pre-registered id, the CIMD document's URL or a DCR registration (§4)
    revokePage,                     // the entry's `revoke.page`, copied at each connect; read once the entry is gone (§3)
    expiresAt, credentialRef, refreshTokenRef, refreshGeneration, credentialHint, // §10.1, unchanged
    pendingAuth } }                 // state, browser nonce, PKCE verifier, expiry; present only mid-connect (§4)
```

The row has no `podId`, no `owner`/`repo` and no `providerRole`. A hosted entry is not repo-shaped: the account's reach is what the provider enforces, and the entry's tools decide which parts of it an agent can touch. That reach includes other people's data: an agent holding a grant reads whatever the vendor's sharing shows the owner, bounded by the vendor and not by the grant's audience. A parameter that names a resource stays inside that reach. Calendar's `list_events` and `get_event` take any calendar's address as `calendarId`, and eight of Linear's pinned getters take an `id` (Vera 76165). Unlike §3's fetch targets, which send the provider to a URL outside the account, these need no exclusion. Calendar's `suggest_time` asks Google for the free/busy of any addresses in `attendeeEmails`, bounded by `calendar.events.freebusy`; it writes nothing and Google's scope intends it, so it stays (Vera 76160). `grantedScope` is what a later write tool will check to tell a row that needs re-consent from one that does not (§5).

**One row per `(createdBy, config.entryId)`.** This is a partial unique index over `hosted-mcp` rows. A second Connect by the same person on the same entry reuses the row: the new pair replaces the old one through the §10.3 fence, and it never creates a second row. If one person held two rows for one vendor, the page could not say which one a grant uses, and the two would go through removal separately. A person with two accounts at one vendor gets one at a time in v1. `providerSubject` is recorded from the first connect, so widening the key later is an index change and not a migration.

**A reconnect as a different account revokes the row's grants.** A grant is made against the reach of the account connected at the time. When a reconnect's `providerSubject` differs from the stored one, `revokeConnectionGrants` runs before the new pair is written. It also runs when the two cannot be compared: either side has no subject, or the two came from different sources (§4). The TASK-148 guard (`toolBrokerService.ts:488–512`) cannot catch this, because the row and its `createdAt` survive the reconnect.

**That reconnect also withdraws the old account's token at the vendor** (the TASK-172 row). The callback drops our copy when it writes the new pair, and the old account's authorization would stay live at the vendor with nothing left on the row that could revoke it. So when both subjects are known, come from one source and differ, the callback sends the old token to the entry's revocation endpoint through `revokeTokenAtVendor` (`services/connectionRemovalService.ts:161`): the refresh token when the row holds one, and otherwise the access token. It runs after the exchange, so a refused exchange withdraws nothing. It reads the old token before the callback's first `connectorSecrets.put`, and no other order works: the put overwrites the secret in place under the same ref (`services/connectorSecrets.ts:116`, `:127`), so afterwards the ref yields the new token (Vera 76175). Nothing is sent when either subject is missing or the two come from different sources, because the two may be one account, and Google would then end the new authorization with the old (§10, step 8). Nothing is sent either when the entry names no endpoint, or when the row's recorded client is not one the row may use (below), as for removal (§9). A `dcr` row's old token goes with the row's own client, the one it was issued to (§4).

**When the old account's grant may still be live, only the person can end it** (Rhea 76176). That is so when a withdrawal is refused or cannot be sent, when it is skipped for a missing endpoint or a client the row may not use, and when the subjects cannot be compared, since only the person knows whether the account changed. The reconnect still finishes. The new pair is written, and the callback lands on the page as connected, naming the entry's revoke page so the person can end the old authorization by hand. A withdrawal is never retried, from the row or later: after the put the ref holds the new token, so a retry would end the authorization just made (Vera 76175).

**The row records which client minted its pair** (76042). The callback writes `config.clientId` with each pair, whatever the client's kind. A refresh token is bound to the client it was issued to (RFC 6749 §6), and RFC 7009 §2.1 has the AS refuse a revocation from any other client. So a row whose `clientId` is not a client it may use is sent to reconnect before any call (§9), and its removal sends nothing. Which client a row may use depends on the kind:

- For `cimd` and `pre-registered`, the snapshot is only compared. A call always uses the client resolved from the entry and the instance (§4), so the row may use only that client. A host move changes a `cimd` client's id, so it sends every `cimd` row to reconnect. Rotating a pre-registered client's secret keeps its id and moves no row.
- For `dcr`, the snapshot is the client the row's calls use, as long as the instance still holds that registration for the entry and issuer, current or retired, and has not seen it refused (§4). A host move retires the current registration and registers a new one for later connects, while the rows minted before it keep refreshing with their own.

Every row connected before this key existed was minted by Linear's CIMD document, since Linear is the only entry so far, so the key arrives in two steps (Vera 76113). The build that writes it refuses only a recorded client that differs, and does not refuse a connected row with none. Old code still mints rows without the key until that build's rollout has finished, and refusing them would send a fresh connection to reconnect. After the rollout, the backfill writes that document's URL to every row that holds a pair without the key. The refusal of a connected row without the key ships with the second entry, not before.

**Only the callback writes a connected row.** The generic `POST /api/integrations` refuses `type: 'hosted-mcp'` by name, as it refuses `github-app` at `routes/integrations.ts:380`. So `createdBy` is always the person who consented, never a field from a request body. Every `config` key this note adds joins `SERVER_OWNED_CONFIG_KEYS` (`utils/serverOwnedConfigKeys.ts:24`). `credentialRef`, `refreshTokenRef` and `pendingAuth` also join `INTEGRATION_SECRET_CONFIG_KEYS` (`models/integrationPublicConfig.ts:23`).

The two references are two new kinds in `connectorSecretKinds.ts` (`:65`), both with provider `hosted-mcp`: an access token at `config.credentialRef` and a refresh token at `config.refreshTokenRef`. That module is the one place a kind is added, and a ref path it does not name is a secret the orphan sweep deletes.

## 3. The catalogue entry, and why upstream cannot write it

Entries live in this repo, one module per vendor, and change only by PR. An entry holds:

- `id`, `title`;
- `resource`: the MCP server URL, which `tools/call` is sent to;
- `audience`, optional: the RFC 8707 resource, when the vendor's protected-resource metadata names one other than `resource` (below). Without it, `resource` is also the RFC 8707 resource;
- `issuer`: the authorization server its protected-resource metadata names, checked at intake;
- `client`: `pre-registered`, `cimd` or `dcr` (§4). A `pre-registered` entry names only the kind: its client's id and secret are instance config, never entry data (§4);
- `scopes`: requested at authorization;
- `revoke`: a `page`, where a person revokes by hand, and also an `endpoint` when the AS's metadata advertises an RFC 7009 revocation endpoint (§9);
- `tools`: each with the name and description an agent sees, the upstream name, a class (`read` or `write`), `irreversible`, a pinned `inputSchema`, and the upstream annotations as seen when the tool was pinned;
- `subject`, optional: one of the entry's own `read` pins and the field of its result that holds the account's stable id, for an AS that offers no `openid` (§4).

Entry ids are checked at load against both the hosted catalogue and the builtin tool Installable ids. They are map keys in the catalogue projection; reusing `github` would replace the GitHub App's metadata and readiness gate. `assertHostedMcpEntries` accepts the reserved-id set from `toolInstallables.ts`, which owns both maps and avoids an import cycle. The named tests prove both the collision refusal and the empty-set control.

**An entry's `audience` is the resource its vendor declares.** The protected-resource metadata at Linear, Atlassian and Google Calendar names each entry's `resource` exactly, at the document built from it (fetched 2026-10-14), so those entries name no `audience`. Airtable's names its bare origin. Its root document, `/.well-known/oauth-protected-resource`, names `https://mcp.airtable.com`. Its `/mcp` document names the same origin, and RFC 9728 tells a client not to use a document whose `resource` differs from the identifier its URL was built from (§3.3). So the origin is the only resource Airtable declares (both fetched 2026-10-14). #2117's capture was granted a token when the request named the origin, and when it named no resource; a request naming `/mcp` has not been measured. Airtable's entry therefore sets `audience` to the origin and keeps `/mcp` as `resource` (Wren, on the TASK-196 row). The entry writes the audience as the metadata does, with no trailing slash, and the intake sends that string unchanged. The sweep of 2026-10-13 found the same split at Otter, Evernote and Front (TASK-196), so it is a field, not an exception for one vendor. Like the rest of the entry, the audience changes only by PR; intake never fetches the metadata.

**The entry load refuses an `audience` that does not cover the URL its token is presented to.** It must be an https URL with the same origin as `resource`, and its path must prefix `resource`'s on a segment boundary: `/` and `/mcp` cover `/mcp`; `/m` and `/other` do not. The port is part of the origin, so a port-only difference is refused. The check runs whenever the key is present, not only when its value is truthy, so an empty `audience` is refused rather than sent (Vera 77023). This rule is what keeps the host a token is minted for the host `tools/call` sends it to. Loosening it to a shared domain or a suffix match would change where a bearer token can go, not just how an entry is written (Vera 77023, 77025).

**`revoke` names its kind because the URL cannot.** Both are https URLs, and only the `endpoint` key decides whether removal calls the vendor (§9). A page that answered that call with 200 would read as a revoke that never happened. A 200 proves no more at a real endpoint, which answers 200 "if the token has been revoked successfully or if the client submitted an invalid token" (RFC 7009 §2.2). Every entry names a page, an entry with an endpoint included, because a removal that cannot revoke at the vendor hands the person that page (§9). So the entry load refuses an entry with no page, a key other than those two, or a URL that is not https, and step 7 (§10) shows the revoke took by something other than its status.

**An entry can leave the catalogue, so removal does not depend on it.** A PR that drops or renames an entry cannot see whether any instance still holds a row naming it, so nothing here relies on entries staying. Each time the callback connects a row, it copies the entry's `revoke.page` to the row's `config.revokePage` (§2). That key is server-owned like the rest, because a PATCH that rewrote it would send the person somewhere else to revoke. Once the entry is gone, the connect routes answer `unknown_entry`, the mint refuses the row `broker_unavailable` (`resolveBrokerFor`, `services/installable/toolInstallables.ts:137`), the broker's credential read refuses it (`services/hostedMcpCredentialService.ts:223`), and removal finishes with the copy (§9). The endpoint is not copied. A token is sent only to an endpoint a current entry names, because the endpoint may be why a PR dropped the entry.

**The entry is the only source for everything an agent sees and everything a grant is checked against.** Upstream can take a tool away or refuse a call. It cannot add a tool, loosen a schema, rename a tool, reword a description or reclassify a tool. The MCP spec (2026-07-28, tools) says "clients MUST consider tool annotations to be untrusted unless they come from trusted servers", and a vendor's server is not one we run. A tool description is also prompt text that reaches every seat holding a grant. An edit made upstream would change every seat's prompt with no review; pinned here, the same change is a PR a gate reads.

**Read permission does not bound egress.** A read tool can make the provider fetch a caller-chosen URL, then return the result into the agent's context. OAuth scope bounds what the credential can change; annotations describe the vendor's claim, and neither constrains where a read result goes. The pinned schema checks argument names, not values: the broker refuses an argument the pin does not declare (below) and forwards the rest as sent, and narrowing a property in the pin only makes the live schema drift. So v1 excludes a whole tool whenever its input lets the caller choose a provider-side fetch target. Linear's `extract_images` accepts free markdown, and `get_attachment` can fetch an external URL named by an attachment when `format` is `content`; both are out. `get_diff` and `get_diff_threads` accept review and GitHub PR URLs as exact keys into Linear, not as URLs to fetch, so they remain.

**Each entry tool becomes a `ToolDefinition`** (`toolBrokerService.ts:16–26`) with:

- `connectionType: 'hosted-mcp'` and the new `entryId`;
- `requiredWriteMode` from the entry's class, and `irreversible` from the entry;
- the pinned `inputSchema`;
- a `call` that forwards to the vendor's `tools/call` under the upstream name.

`getToolDefinitions()` (`:429`) returns the hand-written map plus every entry's definitions. Names are namespaced by entry (`linear.<tool>`), so no two entries collide with each other or with the GitHub tools. Required mode still "comes only from this server-side definition map" (`:700`). The native projection's filter (`grantBrokerProjectionService.ts:180`) reads the definition's `requiredWriteMode`, so it reads the entry's class with no change to that line.

**Drift is a named refusal, not a silent change.** The broker compares each pinned tool with the upstream `tools/list`, taken with the row's own credential. The spec says the list "MAY vary by the authorization presented on the request", so a list taken with any other credential proves nothing about this row. The comparison is cached per row with a TTL, which the build measures (minutes, not per call). For each pinned tool:

| upstream | result for that tool |
|---|---|
| missing | `tool_unavailable` |
| a `read` pin's `inputSchema` differs from the pin only compatibly (below) | offered and callable under the pin's schema, and logged; the annotations row still applies |
| otherwise, `inputSchema` differs from the pin | `tool_drift` until a PR re-pins it: the owner approves canonical args under the pinned schema, and a changed schema can change what those args mean |
| annotations moved toward write since the pin: a claim it recorded (`readOnlyHint: true`, `destructiveHint: false`) is no longer made, or a tool pinned with `readOnlyHint: true` now also says `destructiveHint: true` | `tool_drift`: the hint grants nothing, but a vendor withdrawing it is a reason to stop |
| present and unchanged | offered and callable |

**A `read` pin survives a compatible change upstream, and a `write` pin does not** (Wren 77134–77135). Linear made compatible changes to five of 36 pins in 13 days (connector-ops 77128), and under exact equality each is an outage until a re-pin lands. The comparison is mechanical. Remove the `description` keyword from each schema on both sides, walking only the keywords whose values are schemas. A key named `description` anywhere else is data and is compared, such as a property of that name under `properties` or a key inside an `enum`, `const` or `default` value. A position the walk does not know is compared whole, so the unknown case withholds. The live schema must then equal the pin, except for top-level `properties` the pin lacks and the live `required` does not list. Any other difference withholds the pin: a property removed, retyped or newly required, a `default` changed, a property added below the top level, or an enum changed in either direction. A widened enum withholds because the broker checks names and not values, so a seat could send the new value unreviewed, and a value can open a fetch path, as `get_attachment`'s `format` does above. The annotations are checked as before, and a compatible schema does not excuse a move toward write. A compatible change assesses `ok` with a detail saying so, so the call and the listing need no change of their own (`assessEntryTools`, `services/hostedMcpEntryService.ts:202`). A seat is offered the pin's schema and descriptions, never the live ones.

A `write` pin keeps exact equality, descriptions included. The owner approves canonical args under the pin (§5), and a parameter the vendor adds carries a default the owner never saw, which can change what an approved write does. No entry pins a `write` today. A re-pin is a new pin either way: its PR checks each property the pin did not have against the egress rule above, since seats will be offered it.

**A hosted call carries only the arguments its pin declares.** Today the broker checks only that the arguments are an object (`objectArgs`, `toolBrokerService.ts:131`) and forwards them unchanged (`services/hostedMcpToolDefinitions.ts:292`). Under the compatible rule, a parameter a vendor adds would be one a seat could send the day it ships, offered or not. So the broker refuses `invalid_tool_args` for any top-level argument the pin's `properties` does not name, which also stops a seat sending a parameter the vendor accepts without declaring it. That is the refusal GitHub's tools make (`assertNoUnknown`, `toolBrokerService.ts:138`), made earlier: it runs with the shape check (`toolBrokerService.ts:1125`), so a refused call spends no budget, parks nothing and sends no `tools/call`, and an envelope that parks was checked first. The top level is enough for the compatible rule, because it is the only place that rule lets a schema gain a property; below it, any difference withholds the pin. This check lands before the compatible rule or with it, never after.

Upstream tools that are not in the entry are never offered and never callable, and that is not an error. A drift refusal names the tool and the entry, so whoever reads the trail knows the re-pin is ours to do. `listToolsForGrant` (`:752–791`) is extended to leave out tools refused for either reason, so an agent is not offered what will be refused. Both refusals belong to the broker, before `tools/call` and in that list. A test that calls the comparison directly passes whether or not the broker calls it, so step 4's tests are made through the broker. The two sites are separate checks, and a mutation shows only that the check it deletes is covered: deleting the one in `callHostedTool` does not show that `listToolsForGrant`'s filter is. So step 4 names a mutation for each site. If both sites call one shared helper, one mutation of it covers both, and the PR names that helper (§10, Vera 77076).

**A withheld pin is logged.** Leaving a tool out of a listing tells no one: #2140's first listing left out four granted tools with no log line and no trail row (`toolBrokerService.ts:807`, connector-ops 77128). So each fresh assessment that withholds a pin, or keeps one offered through a compatible change, writes one log line naming the entry, the row and each such tool's verdict and detail. It is written where the assessment is made (`services/hostedMcpEntryService.ts:345`), never per listing or call, so a cached assessment logs nothing. It carries the pin's names and our own detail, never text from the live list.

**A list that fails is not a comparison.** The list is the call's first request. An answer that would fail the call fails it with the same reason (§9), and `tools/call` is not sent. A failed list is not cached, so the next call lists again, and no assessment is used past its TTL, so a vendor that stops answering is never read as unchanged. `createHostedMcpDriftCache` (`services/hostedMcpEntryService.ts:374`) caches no failed list and serves no assessment past its TTL. Its `provider_unavailable` outcome keeps the failed request's own code (`:416–420`), and the call refuses with that code, or `provider_error` when there is none, so the trail names the reason and never `provider_unavailable` (`services/hostedMcpToolDefinitions.ts:222–227`, TASK-199). A credential that cannot be read or refreshed before the list makes a failed list too, and the call keeps that credential's own code (`:225`). `reconnect_required` and `connection_mismatch` are refusals of authority, not outages, so the cache passes them through rather than reporting them unavailable (`hostedMcpEntryService.ts:414`). `listToolsForGrant` still offers the pinned tools after a failed list, a credential's failure included (`toolBrokerService.ts:797–818`). An outage is not a refusal: the call names it when one is made, and a tool left out of the list would name nothing.

**A claim the pin recorded must still be made, and silence withdraws it.** The spec defaults an absent `readOnlyHint` to `false` and an absent `destructiveHint` to `true` (schema 2026-07-28, `ToolAnnotations`), the unsafe value both times. A vendor that stops saying `readOnlyHint: true` or `destructiveHint: false` has withdrawn the claim. A live `destructiveHint: true` also contradicts a recorded `readOnlyHint: true`; the entry load refuses that pair (#2014), and drift does not admit later what the entry refuses. Otherwise a newly spelled default changes nothing, so a pin that recorded neither claim does not drift when the vendor starts saying `destructiveHint: true` (75445, 75449, 75454). Each arm reads the annotations the pin recorded, not its class, and where a withdrawn claim and the contradiction coincide, the refusal names the claim (75457). A `read` pin is not asked to record `destructiveHint: false`: the spec makes that field meaningful only when `readOnlyHint` is `false`, and GitHub's server sets it on none of its 60 read tools (`github/github-mcp-server` at `85598ba`). A vendor that sends `true` there has still said something, and that is what the entry refuses.

**A tool pinned `read` carries the vendor's own `readOnlyHint: true`.** The spec's default for an absent `readOnlyHint` is `false` (schema 2026-07-28, `ToolAnnotations`), so a tool whose vendor says nothing is one the vendor has not called read-only. A pin without the hint would also leave the drift row above dead for that tool, because a pin that never held the hint cannot see it withdrawn (Vera 75423–75424). The entry load refuses such a pin, as it refuses a `read` pin whose annotations say `readOnlyHint: false` or `destructiveHint: true` (#2014). The hint still grants nothing; its absence refuses. **A vendor that sends no `readOnlyHint` gets no entry, not a write-only one** (75440). The class records what a tool does, so a read tool is never pinned `write` to get past a missing hint, and §5's answer on attribution cannot arrive that way.

**Every entry's credential must be unable to write** (76043). A read never parks (§5). With a credential that can write, a tool pinned `read` is kept from writing only by the vendor's word, its annotations, and those can be wrong: Linear's `extract_images` declares `openWorldHint: false` and fetches the URLs in markdown its caller writes (Vera 76034). A scope the vendor enforces holds whatever the pin says, as Linear's `read` does (§4). So an entry requests only scopes its vendor's docs say cannot write. A vendor that offers none gets no entry until it does: Notion, Sentry and Stripe, on the survey of 2026-10-01 (76040), and Granola and Attio, whose only scope is `mcp`, on the metadata of 2026-10-09 (connector-ops 76914, Wren 76915). A server that exposes no write tool today does not meet this bar. Its tool list is the vendor's word and can grow, and one scope already authorises whatever it adds. Any other fence, a vendor's read-only path included, is a new mechanism and a gate item.

**The Linear entry is pinned at build** from a `tools/list` taken on a consenting test account, with read tools only, each re-described by us. The measurement contains 38 tools; the entry pins 36 and leaves out the two caller-chosen fetch paths above. The earlier unauthenticated research named no Linear tools. Linear's MCP docs never mention annotations, so whether its read tools carry the hint is known only from the authenticated list (§11).

## 4. Credentials and intake

**The order is a pre-registered client where the vendor requires one, then a Client ID Metadata Document (CIMD), then Dynamic Client Registration only as a fallback.** The MCP authorization spec (2026-07-28) says DCR "is deprecated and retained for backwards compatibility with authorization servers that do not support Client ID Metadata Documents". Every authorization request and token request carries RFC 8707 `resource`, set to the entry's `audience` when it names one and to its `resource` otherwise (§3): authorization, code exchange and refresh (`hostedMcpIntakeService.ts:349`, `:448`, `:467`). The spec says it "MUST be included in both authorization requests and token requests" and "MUST identify the MCP server".

**Linear uses CIMD.** Its authorization server metadata (fetched 2026-09-27 from `https://mcp.linear.app/.well-known/oauth-authorization-server`) advertises:

- `client_id_metadata_document_supported: true`;
- `code_challenge_methods_supported: ["S256"]`;
- `token_endpoint_auth_methods_supported` including `none`;
- `authorization_response_iss_parameter_supported: true`;
- `revocation_endpoint: https://mcp.linear.app/token`.

Its protected-resource metadata names `https://mcp.linear.app/mcp` as the resource, served by that AS, with scopes `read` and `write`.

With CIMD, our `client_id` is an HTTPS URL on the instance's own API host. That document names the client, its one redirect URI and `token_endpoint_auth_method: none`, and its own `client_id` is its URL. There is **one document per instance per entry**. Each AS therefore sees its own client id with exactly one redirect URI, and the callback path identifies the entry. That is the redirect-per-AS defence against mix-up.

The document has a rate limiter, as every route does (`backend/__tests__/unit/routes/routeRateLimitGuard.test.js`), and a deliberately loose one. The AS fetches it for every member of the instance from a few addresses of its own. A bound sized for one browser would refuse the vendor, and every connect on the instance would fail at once (Vera 75265).

Nothing is registered and no client secret is stored anywhere. A self-hosted instance connects with no setup at the vendor, which a pre-registered client cannot offer, since every instance would register its own app with every vendor. It is a public client: PKCE `S256` on every flow.

**Whether Linear's AS accepts our CIMD end to end is a build measurement.** The research behind this note made unauthenticated GETs of discovery documents only. If it refuses, the fallback is DCR (advertised at `/register`), with one registration per instance per entry and never one per person; its storage is specified below.

**Linear v1 requests `read openid` and nothing else.** Linear's docs say that with only `read`, "the underlying token can’t reach write APIs". So v1's credential cannot write, whatever a grant says, and the §5 rule guards the entry's next version rather than being the only fence. Linear also serves a `/mcp/readonly` path that "only ever exposes read tools". That narrows the list, which the entry already does, not the token, so v1 uses the scope. `openid` is advertised in the AS's `scopes_supported`, and v1 requests it only for `providerSubject`, which §2's account-change rule needs. Whether the AS issues an ID token is measured at build. v1 does not request `email`: the page names a row by its Commonly owner, and a room has no need to see a vendor email.

**Every entry requests the identity scope its AS offers** (the TASK-172 row): `openid` where the AS has it, and never `email` or `profile`, as for Linear above. Without a subject, every reconnect is one §2 cannot compare. It revokes every grant on the row even when the account is the same, and it withdraws nothing at the vendor. Google returns an ID token "only … if your request included an identity scope, such as openid, profile, or email" (developers.google.com/identity/protocols/oauth2/native-app), so Calendar requests `openid` beside its three scopes (§10, step 8).

**An entry whose AS offers no `openid` may read the subject from its own server** (connector-ops 77008 (g), Wren 77045). Of the six vendors below that register by DCR, only Miro's AS lists `openid` (fetched 2026-10-14), and without a subject every reconnect is one §2 cannot compare. Such an entry declares `subject: { tool, field }` (§3). `tool` is one of the entry's own `read` pins, so it carries `readOnlyHint: true`, and its pinned `inputSchema` requires no argument; it is called with `{}` at the entry's `resource`. `field` is a dotted path into the result's `structuredContent`, or, when there is none, into the JSON its single text item holds. Only a non-empty string counts. The entry PR cites the vendor's doc that the field is the account's stable id, never an email or a display name, since either can change or pass to another account. The entry load refuses a `subject` whose `tool` is not one of the entry's `read` pins or whose schema requires an argument, and an entry that names a `subject` and requests `openid`, since a row's subject has one source.

The callback reads the subject after TASK-193's scope check and before it stores or revokes anything. With the new token it lists the server's tools, compares them with the pins as drift does (`assessEntryTools`, `services/hostedMcpEntryService.ts:202`), and calls the subject tool once. No grant is involved and no trail row is written, since no agent made the call. Any failure refuses the connect `subject_unavailable`: the tool missing or drifted, the call failing or answering `isError`, or no string at `field`. That holds on a first connect as on a reconnect, since a row connected without a subject makes its person's next reconnect one §2 cannot compare. The new token goes to `revokeRefusedGrant` (`routes/hostedMcpConnect.ts:100`), which revokes it when the entry has an endpoint and otherwise discards it, as TASK-193's refusal does. The row, its credentials and its grants stay as they were.

**Subjects are compared only when they come from the same source.** The callback records `config.providerSubjectSource` with the subject: `id_token` for the ID token's `sub` (`idTokenSubject`, `routes/hostedMcpConnect.ts:130`), and `tool` for a subject read. A vendor's `sub` and its API's account id need not be the same string for one account, so §2's comparison (`subjectsComparable`, `:480`) treats subjects from different sources as ones it cannot compare. A subject recorded before the key existed reads as `id_token`, its only source until now. So an entry that moves from one source to the other makes each row's next reconnect one §2 cannot compare, once. The key is server-owned, like every key this note adds (§2).

**GitHub is the case CIMD cannot serve.** `github.com/login/oauth` advertises neither DCR nor CIMD, so a GitHub entry uses a pre-registered client: the GitHub App's own, through the user authorization of §10.2 path 1. GitHub's server accepts "GitHub Apps that sign in (are authorized by) a user" (the same `docs/policies-and-governance.md` as §1). That is how per-person GitHub is the same §10 layer (74820).

**A pre-registered client is instance config, never entry data** (76042). Its id and secret are held by the instance, through ESO on the hosted one, and neither appears in an entry or a repo file. The secret appears on no row either. A row keeps only a snapshot of the id that minted its pair (§2), and instance config stays the id's source: every exchange, refresh and revocation reads the id from there, never from a row. The id already arrives that way, as the entry's own `<ENTRY>_CLIENT_ID` (`resolvedClientId`, `services/hostedMcpIntakeService.ts:145`), and the secret arrives the same way. An instance that lacks either does not offer the entry. The entry's readiness answers `not_configured`, as GitHub's does without its App's credentials (`services/installable/toolInstallables.ts:74–76`), so the catalogue projection lists it as unavailable and the page offers no Connect (Vera 76113). A `cimd` entry still has nothing to set, so its readiness stays constant. The instance also treats the entry as one the catalogue no longer has (§3): its rows are refused, and their removal finishes with the row's copied page (§9). The start route's `client_not_configured` stays as the backstop. It is a confidential client: it authenticates with its secret at the token and revocation endpoints, by a method the AS's metadata lists, and it still sends PKCE `S256`. The entry's callback is registered with the vendor as a redirect URI. Google is the first such vendor. Its setup page for its MCP servers says to create a "Web application" client and copy its "Client ID and Client Secret" (developers.google.com/workspace/guides/configure-mcp-servers, updated 2026-09-18). `accounts.google.com`'s metadata lists no registration endpoint and no CIMD support, and names `client_secret_post` and `client_secret_basic` as its token endpoint's auth methods (fetched 2026-10-01).

**A `dcr` entry registers one public client per instance, per entry and issuer, at its first start** (connector-ops 77008 (f), Wren 77045, the TASK-197 row). Six vendors offer DCR and no CIMD: Close, Otter, Buildkite, Miro, Calendly and ClickUp (fetched 2026-10-14). The start registers at the AS's `registration_endpoint` with `token_endpoint_auth_method: none`, the `authorization_code` and `refresh_token` grants, the `code` response type, the entry's scopes, and the entry's callback on this instance as the only redirect URI. It sends PKCE `S256`, as every flow does. Before it sends anything, it refuses `client_registration_unsupported` when the metadata names no https `registration_endpoint`, or when its `token_endpoint_auth_methods_supported` lacks `none`. An omitted list lacks it, since RFC 8414 §2 defaults that list to `client_secret_basic`. It refuses the answer with the same code when the answer registers another method, carries a `client_secret`, or does not echo the one redirect URI. An omitted method is another method, since RFC 7591 §2 defaults it to `client_secret_basic`. An AS that refuses the request ends the start `client_registration_refused`. No `registration_access_token` is stored, and nothing is sent to RFC 7592's management endpoint.

Miro's AS lists only `client_secret_post` and `client_secret_basic` (fetched 2026-10-14), so Miro's PR brings a confidential registration and teaches the orphan sweep who owns its secret. The sweep deletes a secret that no active row names once a 10-minute grace has passed (`services/installable/installableReconciler.ts:272`, `:30`), and a registration is not a row.

**A registration is a record of its own, never a row's.** It holds the entry, the issuer, `clientId`, `redirectUri`, `createdAt`, `retiredAt`, `refusedAt`, and a required `current` flag that every insert writes. A unique index allows one current registration per entry and issuer. It is partial on `current: true`, an equality on a field every insert writes (Vera 77059, #1976). A second unique index keeps a `clientId` to one record per entry and issuer. Two starts at once may both register: the store keeps one, both flows authorize with it, and the other registration stays unused at the AS. A host move changes the callback, so the next start retires the current registration and registers anew, and the rows minted before the move keep their own client (§2).

**Each flow and each row keeps its own client.** The start records its client in `pendingAuth`, and the callback exchanges the code with that client, not with whichever registration is current when the browser returns. For a `dcr` row, `credentialFor` replaces its comparison with the entry's client (`services/hostedMcpCredentialService.ts:377`) with a lookup of the row's own. The row's `clientId` is used while the instance holds that registration for the entry and issuer, current or retired, and has not seen it refused; otherwise the row goes to reconnect (§9). `cimd` and pre-registered rows keep the comparison.

**`invalid_client` refuses one registration, and only its rows.** RFC 6749 §5.2 answers `invalid_client` for an unknown client, and a public client's id is its only credential. When the token endpoint gives that answer to an exchange or a refresh, or the revocation endpoint gives it to a removal, the instance marks that registration refused and keeps the record. The next start registers anew. A connect whose client is refused ends `client_auth_refused` (`routes/hostedMcpConnect.ts:432`). Each row on the registration goes to reconnect before its next call, and its removal sends nothing and returns the page as `revokeAt` (§9).

**An entry may add authorization parameters its vendor requires, from a closed set the code names: today `access_type` and `prompt`** (TASK-172 row, 2026-10-01). Load refuses an entry that names any other key. So no entry restates a parameter the request already sets, such as `client_id`, `redirect_uri`, `state`, `scope`, `resource` or PKCE's. None adds Google's `include_granted_scopes` either: with it, a new token "will also cover any scopes to which the user previously granted the application access" (developers.google.com/identity/protocols/oauth2/web-server), so a Calendar token would carry the scopes of every other entry on the same Google client. Google needs both keys. Its `access_type` defaults to `online`, and `offline` "instructs the Google authorization server to return a refresh token and an access token the first time that your application exchanges an authorization code for tokens". Without `prompt`, "the user will be prompted only the first time your project requests access", and "the `refresh_token` is only returned on the first authorization" (the same guide). Without `offline`, a Google row holds only an access token and goes to `error` with "reconnect" when it expires (`credentialFor`, below). Without `consent`, a reconnect gets no refresh token, and the callback drops the one the row holds (`routes/hostedMcpConnect.ts:415–421`). Google still honours that token, so the comment there gives the wrong reason. The drop is right because the row cannot show that the held token belongs to the new grant, not because that grant is gone. The drop stays, and the withdrawal's PR corrects the comment (§10, step 3).

**An entry whose vendor issues refresh tokens declares what makes every authorization return one** (the TASK-172 row), as a scope it requests or a parameter from the closed set above. Calendar's `offline` and `consent` are that declaration. Without it, a reconnect that gets no refresh token loses the row's to the drop, and the row goes to `error` once its access token expires (`credentialFor`, below). Each entry's walk measures that a reconnect's callback receives a refresh token (§10, step 8). At Google the drop strands nothing only when the dropped token and the newer one are one Google account's. Google's revocation reaches every token that account granted the project, across its clients, so §9's revoke of the newer token ends the dropped one too (§10, step 8). It reaches no other account's grant (Rhea 76177). After a reconnect as a different account, the old grant ends only through §2's withdrawal, or by hand at the revoke page when that withdrawal is refused, skipped or cannot be sent.

**The flow** is the §10.2 route family, one per entry, in the shape of Slack's connect flow (`routes/installables.ts:174`). `POST /api/integrations/connect/hosted-mcp/:entryId/start` takes `auth` and is rate-limited like Slack's. It upserts the caller's row for the entry at `status: 'pending'` if none exists, and writes `config.pendingAuth`: a single-use state bound to the caller and the entry, a second nonce for the browser, the PKCE verifier and a short expiry. It answers with the `authorizeUrl` and sets the browser nonce as an `httpOnly`, `sameSite: 'lax'`, `secure` cookie whose path is the callback's. The page then sends the browser to the vendor. A row that is already connected keeps working while this happens, the way Slack's `pendingBind` works.

The page's call to start passes `withCredentials: true`, as Slack's does (`frontend/src/v2/components/V2ConnectorsPage.tsx:588`). The API is on another origin from the app, so without it the browser drops the cookie and every callback refuses. A backend test sets the cookie itself and cannot see this. The page's test asserts the flag, as the Slack arms do (`frontend/src/v2/__tests__/V2ConnectorsPage.test.tsx`), and step 7's walk on the deployed build shows that a real browser keeps the cookie.

`GET …/:entryId/callback` is a browser redirect with no bearer token, so it checks two secrets, as Slack's does (`routes/installables.ts:283–301`). The state names the flow, and the cookie proves that the browser finishing it is the one that started it. The state alone binds nothing. It travels in a URL that the starter holds and can hand to someone else, and if that person approved, their tokens would land on the starter's row (Vera 75250). A callback with no cookie refuses `invalid_state` before it looks up the row. A cookie that does not match the row's nonce, compared in constant time, refuses `browser_mismatch` without consuming `pendingAuth`, so a wrong browser cannot burn a real flow. The callback is rate-limited by address, as Slack's is (`:383`). Unlike Slack's, a throttled callback still redirects to the page, with `rate_limited`. Its caller is a browser mid-navigation, and every outcome of the callback lands where Connect can be offered again, not on raw JSON (Vera 75269). It refuses a state it did not issue, a used state and an expired state. It refuses an `iss` that is not the entry's `issuer`, per RFC 9207, since Linear advertises it. It exchanges the code at the entry's token endpoint with `code_verifier` and `resource`. A returned scope list is parsed on spaces or commas and checked against `entry.scopes` before any credential is stored or any earlier credential is revoked: an extra scope refuses this callback and attempts refresh-token revocation (or access-token revocation when there is no refresh token) for the newly returned token when the entry has an endpoint. An entry with only a revoke page cannot withdraw it: the token is discarded unstored (`routes/hostedMcpConnect.ts:105`), and the grant stays on the vendor's page until the person removes it there. Airtable is such an entry. Miro and ClickUp advertise no revocation endpoint either (connector-ops 76914), nor do Buildkite and Calendly (fetched 2026-10-14). An omitted `scope` means the requested set by RFC 6749 §5.1; a subset is accepted and recorded. The check also runs on reconnects; a refused reconnect leaves the existing credentials, connection status, and grants unchanged, though its one-shot `pendingAuth` was already consumed. Rows connected before this check are not backfilled or re-checked outside a callback. The accepted pair is then written through the §10.3 fence and `pendingAuth` is cleared. A pending row is never grantable, because the mint requires `connected`. Once its expiry passes it holds nothing secret, and the next start overwrites it.

**`credentialFor(connection)`** (§10.3, `services/hostedMcpCredentialService.ts:348`) is the only place the access token is decrypted. It refreshes behind the fence, and `call` sends the token as a bearer to the vendor's Streamable HTTP endpoint and nowhere else. Every refresh is treated as rotating, whatever the vendor does, which is the case the fence exists for. The spec says clients "MUST NOT assume refresh tokens will be issued"; an AS that issues none gives a row whose `expiresAt` is the access token's, and when that passes the row goes to `error` with "reconnect" (`:407–422`). An AS that also omits `expires_in`, which RFC 6749 §5.1 only recommends, gives a row with no `expiresAt`. `credentialFor` reads that as expired (`:315–321`), so the row goes to `error` on its first call; the null is the callback's (`routes/hostedMcpConnect.ts:571`). An entry whose vendor issues no refresh token therefore enters only if its token response carries `expires_in`, measured at capture; otherwise it waits for a gated change (Wren 76916). Linear's MCP token lifetimes are not in its metadata and are measured at build. No agent environment, tool result or trail row ever holds the token.

## 5. When a hosted write is the member's own act

In member mode, whatever an agent writes appears at the vendor as the member. [linear-connector-scope.md](linear-connector-scope.md) §2 refused Linear's `actor=user` because it "attributes an agent's words to a human". This type narrows that refusal rather than reversing it. **A read is delegated access. A write counts as the member's own act only when all four of these hold:**

- **(a) Every non-read call parks.**
  - The mint refuses `writeMode: 'write'` on a `hosted-mcp` row, with `write_requires_confirm`.
  - Attenuation cannot raise a mode (`roomGrantService.ts:346–348`, `grant_not_attenuated`), so every grant descended from one on this row is `read` or `write-with-confirm`.
  - Under `read`, a non-read tool is refused `write_mode_not_allowed` (`:417–418`).
  - Under `write-with-confirm`, every non-read call parks for approval (`toolBrokerService.ts:717–718`). A `write` grant would run non-read, non-irreversible calls without parking, so the mint refusal is what makes the rule hold.
- **(b) Only the owner approves.** `approvalActionService.ts:493` refuses anyone but the pending call's `ownerUserId`, and `:502` refuses a bot. For this type, `ownerUserId` is the Connection's `createdBy`, carried as it is today (`toolBrokerService.ts:519`, `:742`).
- **(c) The owner sees what they approve.** `V2ApprovalCard.tsx` fetches the pending call's canonical args for the owner only (`:99`, "Approval buttons must not allow an owner to approve blind") and renders them (`:203`).
- **(d) What runs is what was approved.** `executeApprovedToolCall` refuses `args_digest_mismatch` (409) when the args no longer match the approved digest (`toolBrokerService.ts:842–843`).

Under these four, the member has read and approved each written call, one at a time. Reads carry no words of the agent's, so they need none of the four. v1's Linear entry has no write tool, and its credential has no `write` scope. A write tool added later also needs re-consent with `write`, and `grantedScope` is how the page tells which rows need it. That alone does not meet §3's bar: the same token would serve every read in the entry, and a read never parks. So the first entry with a write tool also needs a mechanism that keeps a credential able to write away from every call that has not parked. That mechanism is a gate item, specified with that tool, not here. So is a parked call that outlives a re-pin of its tool: approval binds the arguments and the tool's name, not the pin, so a call parked before a deploy that re-pins its tool would run under the new pin.

**A parked call is still a call, so the seat that made it learns how it ended** (TASK-208). When a call parks, the seat's `tools/call` answers `pending_approval` with the card's `approvalId` (`routes/mcpGrants.ts:116–121`), and that turn ends. Today nothing reaches the seat after that. #2161 wakes the proposer of an approved `commonly_propose_action` card and leaves a parked call out on purpose, because what a call returns is the broker's to say.

- **Approval runs the parked call once, as approved.** The winning resolver executes the copy of the envelope it took before the stored args were scrubbed (`approvalActionService.ts:601`, `:676`), through `executeApprovedToolCall` (`toolBrokerService.ts:1282`). That path checks the digest, the grant, the audience, the connection, drift and the budget immediately before the provider, and never parks again (§6).
- **Each ending reaches the seat once, as `approval.resolved`**, the type #2161 adds, with `actionType: 'tool_call'` and the `approvalId` the seat got at the park. A parked call ends in one of five ways:
  - approved, and it ran: `ok`;
  - approved, and it failed at the vendor: `failed`, with §9's reason;
  - approved, and refused: `refused`, with the code. A refusal can come before the budget reservation, from a check such as `grant_expired`, `tool_drift` or `budget_exhausted`, or after it, from the vendor refusing the call on its own authority, as with a 403 or a refresh refused `invalid_grant` (§9);
  - declined;
  - expired undecided.

  Only the transition that moves the card out of `flagged` enqueues the event, so a second click, or a sweep racing a decision, delivers nothing more. A failed enqueue is logged and never undoes the decision, as in #2161. The CLI branch TASK-207 adds returns `payload.content` for every `approval.resolved`, so a tool call needs no branch of its own, provided that branch does not filter on `actionType`.
- **A decline and an expiry are delivered too.** This differs on purpose from #2161's rule for a proposal, where a no wakes nothing. A declined proposal leaves nothing outstanding. A parked call has left the seat telling someone it is waiting, and for a seat grant the card sits in the owner's room with the agent (`toolBrokerService.ts:871–885`), where the person who asked may never look. A seat that proposes again parks again, so a repeat always waits on the owner.
- **The event says how the call ended, never what the vendor said.** The server composes `payload.content` from our own text, the pin's tool name, the approver's name, the ending and its code. It never carries the vendor's result or error text, the arguments, or a credential. Both runtimes give `payload.content` to the model as the turn's prompt (#2161, "Runtime coverage"), so vendor text placed there would reach a seat as an instruction rather than as a tool result. §3 lets no live vendor text into what a seat is told about a tool, and this applies that rule to the cue. #2161's cue quotes an executor's error message (`describeApprovedOutcome`). For a proposal that message is ours, but for a hosted call it can be the vendor's (`hostedMcpToolDefinitions.ts:323`), so a tool call's cue names the code instead.
- **A seat that needs what the call produced reads it back** with a read tool, where it arrives as a tool result, confined, trailed and budgeted like any read. The one exception is a receipt that the write tool's definition declares: named fields of the result, each with a shape that cannot carry prose, such as an integer or a fixed identifier pattern. Each value is checked on its way into the cue, and one that fails is dropped. A tool that declares no receipt delivers the ending alone. GitHub's write tools may declare their issue or pull request number in the build, and a hosted write tool declares its receipt in the PR that adds it, with the gate item above.
- **The card and the room carry the ending, not the result.** The card keeps a parked call's arguments to the owner (`approvalActionService.ts:73`), but two fields on `main` can still put the vendor's words on it. `executionResult` holds the vendor's result (`:679`, copied to the card at `:83`), and a write's result can repeat the arguments it was given. `executionError` holds the error's message (`:721`). For a `tool_call`, the row keeps the ending, its code and the ending's trail `callId` instead. The record still links to its execution, through the trail, as it already links to the arguments only through their digest (ADR-020 D2). The room receipt says `done` for every call that returns (`:687`), including one the vendor marked `isError` (`toolBrokerService.ts:1059`), so it names the ending as well.
- **The grant is checked when the call runs, not when it parked.** Approval is consent to one call under the grant as it stands at execution, and it never extends or revives a grant. A grant expired or revoked since the park (`roomGrantService.ts:430–431`), a seat that has left the audience, an owner banned since (§7), a pin that has drifted or a tool gone upstream (§3), or a spent budget each refuses the call with its own code, and the seat learns that code. A parked call's card expires closed after 24 hours (`models/ApprovalAction.ts:78`, `approvalActionService.ts:612`), where a proposal's stays decidable. The build caps that deadline at the grant's `expiresAt`, so a card never outlives the grant it would run under, as a grant is capped at its Connection's (§9).
- **Budget is spent when the call runs, never when it parks.** The park returns before the reservation (`toolBrokerService.ts:1145–1233`, then `:1236`). Execution reserves one call against the grant's lineage after every other check and just before the provider (`:1317–1321`). So a declined or expired call spends nothing, and neither does one refused before the reservation. Reads spend from the same budget while a write waits, so an approved write can find it spent. It is then refused `budget_exhausted`, because approval does not lift the granter's bound. A reserved call has spent its reservation whether it runs, fails or the vendor refuses it, as an unattended call does.

## 6. Which surface may offer a hosted write tool

This answers Vera 74793/74794, in Kai's wording (74826). Three surfaces can call a hosted tool:

- the grants-MCP endpoint a seat's runtime loads (`POST /api/mcp/grants/:grantId`, `routes/mcpGrants.ts:94`);
- the native-runtime projection (`grantBrokerProjectionService.ts:258`);
- a direct call.

All three end in `toolBrokerService.callTool` (`:685`). **For every call an agent makes, the park is one function, so it is the enforcement, and no surface routes around it.** The native projection offers only read tools, `getToolDefinitions().filter((definition) => definition.requiredWriteMode === 'read')` (`:180`). That is an **offering filter, not the enforcement**: a write reaching `callTool` from there would hit the same park. This corrects the TASK-172 ruling's part 3, which called `:180` enforcement.

One path reaches the vendor without passing the park, and it is the approval itself (Vera, 74860). `definition.call` has two call sites: `:799` inside `callTool`, past the park, and `:861` inside `executeApprovedToolCall` (`:833`), which runs only from `approvalActionService.ts:595` once the owner approves. That path never re-parks, by design, so its gate is (b) and (d), not (a). The owner check lives in its caller (`approvalActionService.ts:493`, `:502`). The digest check at `:842–843` is inside it, but compares the args against whatever `expectedArgsDigest` the caller passes; today both come from the approved row (`approvalActionService.ts:671–672`). Nor does the function bind to an approval: `approvalId` is only written to the trail rows (`:868`, `:879`), never checked against a parked call, and the row it reads is the grant, by `grantId` (`:845`; Vera, 74864). **A second caller of `executeApprovedToolCall` inherits no park, no owner check and no approval binding. It must check the owner itself and take the args and the digest from the owner-approved record.**

So:

- **the grants-MCP surface is the only surface that may offer a hosted write tool, and every non-read call parks there for the owner**;
- the native projection offers none, through the existing filter reading the entry's class;
- a direct call is the same function.

`tools/list` already follows the grant (`listToolsForGrant`, used by the endpoint's ListTools handler since TASK-146), so a `read` grant lists no write tool on any surface.

**A seat that cannot be confined is offered no hosted tool, reads included** (Kai, 74877). A hosted grant reaches a seat through the same grants endpoint as every grant, so it inherits TASK-063's refusal unchanged, and that refusal drops the whole entry, not a tool class. The server withholds the entry at the projection (`routes/agentBinding.ts:115`), the daemon withholds it again (`withholdGrantBroker`, `cli/src/lib/grant-broker-guard.js:230`), and the pi client refuses the broker's path (`cli/src/lib/adapters/pi-mcp-client.mjs:39`, `:68–74`). The two halves reach pi by the same rule: each admits only the adapters known to confine, claude and codex. The daemon's list is `ADAPTERS_WITH_GRANT_BROKER` (`cli/src/lib/default-environment.js:51`, read at `grant-broker-guard.js:180`). The server's is `CONFINING_ADAPTERS` (`backend/services/grantBrokerConfinement.ts:74–77`, read at `:204`), which became an allowlist on 2026-10-09. Until then the server refused only the adapters it knew could not confine, so an adapter nobody had judged passed it. Both refuse a pi seat `grant_broker_unconfined`, reason `adapter_cannot_confine`, so it gets no Linear tool at all.

That is intended, and there is no read-only arm. A read never parks (§5). On a seat nothing confines, the park still stops each write for the owner, but a read's result goes wherever the seat can send it, and confinement is the only bound on that. An arm that admitted reads to such a seat would admit exactly the calls the refusal exists for. The refusal is a named state (§9): the grant read returns it, with the fix in its detail, which is to move the seat to claude or codex (`routes/grants.ts:239`). No page on `main` reads that field yet, so the grant's page must show it before step 7's walk (§10).

The refusal must also hold where the tool runs, not only where the entry is offered. The grants endpoint evaluates the server's predicate (`grantBrokerRefusal`) for the calling seat, on `tools/list` and before `callTool` on `tools/call`, and trails a refused call `refused`, not spent. That was ruled on TASK-111 (2026-09-23) and is TASK-175, built before the mint admits the type (§10, step 4). Since both rules list what they admit, an adapter added to the CLI later is refused by the daemon, and by the server wherever the seat names its adapter, until each list admits it. A test on each side pins its list to claude and codex (`backend/__tests__/unit/services/grantBrokerConfinement.test.js:37`, `cli/__tests__/adapter-confinement-parity.test.mjs:23`), and the CLI's also pins the adapters it withholds, OpenCode, pi and Qwen (`:24`).

**What each arm can witness.** v1's Linear entry has no write tool, so these arms run on a test entry that has one, against a stub MCP server. They witness the mechanism, not Linear.

- **The park, through the grants endpoint.**
  - A `write-with-confirm` grant on a hosted row: calling the write tool with `tools/call` parks it, and the stub sees no call.
  - When the owner approves, the stub sees exactly one call, with the canonical args.
  - Approval by another member is a 403, and by a bot is a 403.
  - Args changed after approval give a 409.
- **The filter, through the projection.** For a grant that names the write tool, the projection offers no write tool at all.
- **The mint.**
  - `write` on a hosted row is refused `write_requires_confirm`.
  - Attenuating `write-with-confirm` to `write` is refused `grant_not_attenuated`.
- **A `read` grant.** The write tool is absent from `tools/list`, and calling it anyway is refused `write_mode_not_allowed`.
- **A seat that cannot confine.** A pi seat in the grant's audience is refused, never parked: the projection and the daemon withhold the entry with `grant_broker_unconfined`, reason `adapter_cannot_confine`, and the grant read names it. A read tool's `tools/list` and `tools/call` reaching the endpoint anyway are refused with the same code, and the stub sees no call.

## 7. What changes in the mint, the broker and the catalogue

**`installationId` is the row's `_id`.** On a hosted grant, `connectionId` = `installationId` = the row's `_id`. The row has neither installationId slot: top-level `installationId` (`models/Integration.ts:184`, unique and sparse) and `config.installationId` (`:213`) both stay unset. That rests on who writes to the row: its only writers are its own connect routes (start and callback, §4), which write neither slot; the generic route refuses the type; and `config.installationId` is already server-owned. The mint's `connection.installationId || connection.config?.installationId` (`routes/grants.ts:309`) would come out empty and be refused `invalid_installation` (`:313–314`), so the mint sets it to the `_id` for this type. An `_id` is never reused, so the TASK-148 class, a grant matching a re-created row by an external id, cannot arise.

**The mint** (`routes/grants.ts:298`):

- It accepts `hosted-mcp` beside `github-app` at the type check (`:310`). For this type it also requires `connected`, no `revokedAt`, a `credentialRef`, and an entry the catalogue still has.
- It refuses `write` (§5).
- `resolveBrokerFor` (`:352`) takes the row, not its type. For this type it returns that entry's tools, so `invalid_tools` (`:353–360`) refuses a tool from another entry.
- The granter check (`connectionOwnerId`, `:265–267`) is unchanged, because `createdBy` is the person.
- TASK-147 lands with removal, in step 6 (§10), and the first catalogue entry does not ship without it. This is the second grantable type, so every path that can remove the row must call `revokeConnectionGrants` before the row moves, witnessed per path. `DELETE /api/integrations/:id` already does (`routes/integrations.ts:797`). Pod deletion (`controllers/podController.ts:730`, `deleteMany({ podId })`) and the reconciler's and admin Installable routes' updates, which match on the top-level `installationId`, cannot reach a row that has no `podId` and no installationId slot. The witness for those paths is that a hosted row and its grants come through untouched. Pod deletion never calls a vendor. If a writer ever gives a grantable row a `podId`, the fix is to keep that row out of the sweep, not to route the sweep through removal. The row belongs to its owner, not to the pod, and `DELETE /api/integrations/:id` removes it. §2's account change is the one new path, and it revokes.
  - The legacy Discord delete (`routes/discord.ts:241`) looks its row up by `installationId` and `type: 'discord'`, so the same witness covers it.
  - Pod deletion's case also needs the row to stay without a `podId`. `PATCH /api/integrations/:id` can set one on a user-scoped row, and it refuses a hosted row only because that row holds no `config.linkedUserId` (`routes/integrations.ts:672`). A witness pins that refusal.
  - Deleting a member's Commonly account (`DELETE /api/admin/users/:userId`, `routes/admin/users.ts:267`, behind both admin pages' Delete) moves no row. It deletes the person and nothing else, because `User` has no delete hook. The broker's owner check (below) stops the grants, but the row stays active, so the orphan sweep would keep a live refresh token for a person Commonly no longer has, and nothing would revoke it at the provider. The route therefore refuses `409` while the person owns a hosted row. Its body lists each row's `_id` and entry, which is what `DELETE /api/integrations/:id` takes; that route admits an admin (`canDeleteIntegration`, `routes/integrations.ts:171`) and runs §9's removal. Removal stays one path with one retry, not a second copy inside account deletion.
  - A ban (`PATCH /api/admin/users/:userId/ban`, `:233`) moves no row either, and it is the likelier way a member leaves (Vera 75492). From then on `auth` refuses the person (`middleware/auth.ts:74`), so they cannot revoke anything themselves. Neither path to the broker passes `auth`, though: `routes/mcpGrants.ts:50` runs `agentRuntimeAuth`, and the native runtime calls it in process (Vera 75494). So the ban reaches the person's grants only through the broker's owner check, which refuses them for as long as the ban lasts; lifting the ban restores them with no reconnect. The ban route stays unguarded, because a ban may be urgent and it can be lifted. The material stays for the same reason; an admin who wants the credential gone removes the row.
  - The mint may admit the type before any of this lands. No hosted row can exist while `HOSTED_MCP_ENTRIES` is empty, so no hosted grant can either.

**The broker** (`resolveConnection`, `toolBrokerService.ts:455`):

- For this type it finds the row by `findById` only (Kai 74792), never through the `installationId` lookup at `:461`.
- It checks the type, `status`, `revokedAt`, that the entry exists and that a `credentialRef` is present.
- It checks that the definition's `entryId` equals the row's, the same `connection_mismatch` class it applies to type today (`:476–486`).
- It keeps the TASK-148 `createdAt` guard (`:488–512`) unchanged.
- For a hosted row, it refuses when the row's owner is no longer a usable account (TASK-181). It reads the owner through `sessionAccountService` (`loadSessionAccount`, `sessionRefusal`), the one definition the session verifiers share, and renders the answer as `connection_owner_banned`, `connection_owner_missing` or `connection_owner_bot` (403, beside `connection_superseded`). Separate codes tell an admin which remedy applies: lift the ban, or remove the row so its owner can be replaced (Vera 75498). `listToolsForGrant`, `callTool` and `executeApprovedToolCall` all resolve through it, so one check covers the offer, the call, and a call approved after the ban. It reads live state at call time, so nothing is written when the ban is set and a lifted ban needs no reconnect. Both call paths' existing catch writes the refusal to `tool_calls` as `refused`, with the code as `reason` (`safeReason`, §9). A refused list writes no row, because a list is not a call; the seat gets the code as a JSON-RPC error (`routes/mcpGrants.ts:73`). A `github-app` row is unchanged: its token belongs to the app installation, not to the admin who created the row.
- `ToolConnection` (`:28–34`) widens to both types; `owner`/`repo` belong to `github-app`, and `entryId` to `hosted-mcp`.

**The catalogue.**

- `TOOL_INSTALLABLES` (`services/installable/toolInstallables.ts:58–65`) gains one tool Installable per entry, built from the entry, and `resolveBrokerFor` (`:124–139`) keys on the entry.
- The catalogue filters connections by `meta.connectionType` (`installableCatalogService.ts:97–119`); for this type it also filters by `config.entryId`, so the Linear Installable lists only Linear rows.
- `publicConnection` already falls back to `_id` for `connectionId` (`:78–79`).
- `IntegrationType` (`models/Integration.ts:13`) and the model's `type` enum (`:203`) gain the value.

## 8. The trail records whose credential ran

`ToolCallRecord` (`models/ToolCall.ts:62–75`) records the grant, the agent, the tool and the outcome, but not whose credential ran. With per-person Connections, that is the first question a trail reader asks: whose Linear was this?

**Every record gains `credentialOwnerId`, the Connection's `createdBy` at call time, for every type.** That includes `github-app`, whose owner is the admin who created the row. It is copied onto the record, because once §10.5's last step deletes the row there is nothing left to join to. The copy holds against the row's delete, not the person's: once a Commonly account is deleted (§7), the id resolves to no one. A name beside it would hold against both, but how long a deleted person's name is kept is a retention decision for account deletion as a whole, and this column does not make it. Soft-deleting the row instead was considered and rejected: §10.5 ends with the delete, and a soft-deleted row is one that the sweeps, the catalogue and the mint would all have to learn to skip.

## 9. Failure is named (C9, C10)

| at the vendor | what the broker does | trail (outcome, reason) | row |
|---|---|---|---|
| 401 on a call | one fenced refresh (§10.3), then one retry | as the retry ends | untouched on success |
| `invalid_grant` on that refresh | fails the call | `refused`, `reconnect_required` | `status: 'error'`, "reconnect"; only the generation holder writes it (§10.3), and later calls are refused as §10.3 says |
| 403 or `insufficient_scope` | fails the call | `refused`, `provider_denied` (§10.4) | recorded, so the page can say what was refused; the grant is not touched |
| 429 | fails the call | `failed`, `provider_rate_limited`, with `Retry-After` when one is sent | untouched |
| 5xx, a timeout, no connection | fails the call | `failed`, `provider_error` or `provider_unreachable` | untouched |
| a result with `isError: true` | preserves the vendor content and marks the tool result as an error | `failed`, `upstream_tool_error` | untouched |
| a pinned tool missing, or drifted (§3) | refuses before calling | `refused`, `tool_unavailable` or `tool_drift` | untouched |
| an argument the pin does not declare (§3) | refuses before calling, parking or spending budget | `refused`, `invalid_tool_args` | untouched |
| the row's owner banned or gone (§7) | refuses before calling | `refused`, `connection_owner_banned`, `connection_owner_missing` or `connection_owner_bot` | untouched, and so is the grant |
| `invalid_client` on a `dcr` row's refresh | marks the registration refused (§4) and fails the call | `refused`, `reconnect_required` | `status: 'error'`, "reconnect"; the registration's other rows are refused by the line below before their next call |
| the row's `clientId` is not a client the row may use (§2) | refuses before calling | `refused`, `reconnect_required` | `status: 'error'`, "reconnect"; written only while the row still holds that `clientId`, so a reconnect that lands first stands |

`refused` is for answers about authority, whether ours or the vendor's; `failed` is for a call that could not complete (`ToolCallOutcome`, `models/ToolCall.ts:21`). Each row reaches the person as a named state, never as a silent empty result.

**A parked call ends once, and its ending is trailed** (TASK-208). The park writes `pending_approval`, `approval_required` (`toolBrokerService.ts:1217`), and the ending writes one more row under the same `approvalId`:

- approved: the execution's own row, as for any call (`:1322`, or `:1332` when it throws): `ok`, `failed`, or `refused` with the code, whether a check of ours stops it before the provider or the vendor refuses it;
- declined: `refused`, `approval_declined` (`approvalActionService.ts:725`);
- expired: `refused`, `approval_expired`. The decide path writes it (`:627`). The usual path is the scheduler's five-minute sweep, `sweepExpiredToolCallApprovals` (`approvalActionService.ts:766`, scheduled at `schedulerService.ts:491`), which writes no row, so a call it expires ends with nothing in the trail after `pending_approval`. The build writes the same row there.

The seat learns each ending through §5's event, and the owner sees it on the card.

**Removal** is §10.5 unchanged in order:

1. Grants: `revokeConnectionGrants`, which matches a grant by the row's `_id`, the id every hosted grant is stored under.
2. The row goes to `disconnected`, and `isActive` stays true: step 3 needs the token, and the orphan sweep revokes the material of a row that is not active.
3. The provider, by whether the entry's `revoke` names an `endpoint` (§3), never by a URL. A revoke that took ends with §10.5's mark, and a retry that finds the mark skips this step.
   - With an endpoint, the call sends the refresh token when the row names one, and otherwise the access token, each with its RFC 7009 `token_type_hint` (Linear's endpoint is `https://mcp.linear.app/token`). Unlike §10.5's GitHub grant-deletion call, which takes an access token, this sends the token itself, so it needs no refresh first. No call sends an empty token.
   - Only a 2xx counts as revoked. Any other answer, `invalid_grant` included, is a refusal: the row stays with its references, and the response is `502 provider_revoke_failed` with the page as `revokeAt`. RFC 7009 answers a token that is already gone with 200. RFC 6749 §5.2 also gives `invalid_grant` for a token "issued to another client", and a `cimd` client id is a URL on the instance's API host (§4), so after a host move a revoke can answer that way while the authorization stays live.
   - Nothing is sent when the entry has no endpoint, or when that token's secret is not found. Nothing we hold can revoke then, and a kept row only waits for a retry that can never succeed, so the removal finishes and the response carries the page as `revokeAt`, as §10.5 does for a pasted token. A secret that cannot be read for any other reason is a 502 with the row kept, since it may be readable later.
   - Nothing is sent when the row's entry is no longer in the catalogue either (§3). The removal finishes the same way, with the row's `config.revokePage` as `revokeAt`. Keeping the row would keep a live token that nothing may use, waiting on a PR that may never restore the entry. While the entry is present, its own page is used instead of the copy, since a PR may have corrected it. A row whose entry is gone and which holds no copy keeps today's refusal, `provider_revoke_failed` with the row kept, because a removal that finishes must hand the person a page. The catalogue is empty today and the copy lands before its first entry (§10), so every row will hold one.
   - Nothing is sent when the row's `clientId` is not a client the row may use (§2). That includes the host move above, which changes a `cimd` client's id and is now caught before any send, and a `dcr` registration the instance has seen refused (§4). RFC 7009 §2.1 has the AS refuse a revocation from a client the token was not issued to, so a send could not be relied on, and a kept row would wait for a retry that may never succeed. The removal finishes with the entry's page as `revokeAt`, as for a token whose secret is not found. A `dcr` row whose registration was only retired still revokes, with its own client.
   - One answer other than 2xx finishes a removal: `invalid_client` to a `dcr` row's revoke. It marks the registration refused (§4), and the removal finishes as above, since nothing the instance holds can revoke that token then.
4. The material.
5. The delete.

A grant's `expiresAt` is capped at the Connection's when the row has one (§10.4).

## 10. Build order and named tests

Each step can be tested without the vendor, except the live measurements in steps 3, 7 and 8.

1. **The type and the record.** The enum and union, the partial unique index, the two secret kinds, and the config-key registries.
   - `a hosted-mcp row cannot be created through the generic route`
   - `a hosted-mcp row's credential references never leave the server` (extends #1673's)
   - `a channel connector row cannot be granted` (§10.0, unchanged)
2. **The entry, its projection and drift.**
   - `an upstream tool not in the entry is never offered`
   - `the upstream description never reaches an agent`
   - `a pinned tool missing upstream is refused tool_unavailable`
   - `a pinned tool whose schema changed upstream is refused tool_drift`. Its fixture adds an optional top-level property to a `read` pin, which §3's compatible rule makes `ok`, so with that rule it moves to an incompatible change and the addition becomes an arm below.
   - The compatible rule (§3):
     - `a read pin whose upstream adds an optional top-level property, or changes only a description, is ok`, with a detail saying so
     - `a read pin is refused tool_drift when upstream removes, retypes or newly requires a property, changes an enum or a default, or adds a property below the top level`, one arm each
     - `a property named description is compared, not stripped`, with a `default` whose value holds a `description` key among its arms
     - `a write pin whose upstream adds an optional property is refused tool_drift`; its mutation applies the read rule to every pin
     - `a compatible schema does not excuse annotations moved toward write`
   - `a read pin carrying no readOnlyHint is refused`, with #2014's other entry-time refusals (§3)
   - the annotation arms (§3): a `destructiveHint: false` gone silent is `tool_drift`; a pin that recorded `readOnlyHint: true` whose tool now also says `destructiveHint: true` is `tool_drift`; a pin that recorded both claims, against that same tool, is refused naming the `destructiveHint: false` it lost; a `destructiveHint: true` newly spelled on a `write` pin that recorded neither claim is `ok`
   - `an entry whose audience is empty, not https, of another origin, or a path that does not prefix the resource's on a segment boundary is refused at load`, with a port-only difference and a same-origin sibling path among its arms (§3)

The CTO ruled on #2168 on 2026-10-14. A grant from a source that outsiders can write is refused while any agent in its pod can cause an outward effect without a person. It is allowed with no override when every such effect is approval-gated: a parked call that waits for a person's Approve, on a card that shows the canonical arguments. Anything else needs the owner's override for that source and those tools, recorded and shown on the Tools page, and revoking either side ends it. Part 1's untrusted marker applies either way, and vendor blocks stay byte-identical. This section is the design note the ruling asks for before any code, and the build is its own row. The code it cites is read at `main` `8a3a93ac`.

**The reach.** A grant's reach is the set of pods its results can be posted into without leaving the people the grant was made for. For a pod grant it is the target pod. For a seat grant it is every pod the seat is a member of or installed in, because the seat carries the grant into each of them. An attenuated child keeps its parent's target (`attenuateGrant` is passed none, grants.ts:426), so it has its parent's reach.

The check counts every agent that is a member of, or installed in, a pod of the reach, not only the grant's audience. The audience reads the outsider's text and posts what it read, and every agent in the pod reads that post.

**(a) What counts as an outward effect.** An agent holds an outward effect when it can do any of the following without a person's Approve. For a grant, the check produces a list of `(agent, effect, where)` entries, and the default refuses when that list is not empty.

1. **A DM.** `POST /api/agents/runtime/agent-dm` (agentsRuntime.ts:1049) is `commonly_dm_agent` in the MCP server and `commonly_open_dm` in the openclaw extension. It is always outward: an agent-dm pod can be read by every human who shares any pod with either agent (ADR-001 §3.7), not just by the reach. The route refuses only a target that shares no pod with the caller (:1186), so every agent that calls the runtime API holds it. The native runtime's tools do not include it.
2. **Joining or creating a pod.** `POST /pods` (:3038) is `commonly_create_pod`, which creates a pod or joins a joinable one of the same name. `POST /pods/:podId/self-install` (:3259) is `commonly_self_install_into_pod`. Both are always outward, because each can add a pod outside the reach to the places the agent can post.
3. **Writing into a pod outside the reach.** This covers every kernel write that lands in a pod:
   - messages: `POST /pods/:podId/messages` (:2056) serves `commonly_post_message`, and `commonly_attach_file` posts through it too;
   - thread comments (`commonly_post_thread_comment`) and reactions (`commonly_react_to_message`);
   - the task board (`commonly_create_task`, `commonly_claim_task`, `commonly_complete_task`, `commonly_update_task`);
   - decision cards (`commonly_request_decision`) and asks (`commonly_ask_agent`, `commonly_respond_to_ask`);
   - the native runtime's `commonly_post_message` and `commonly_create_task` (nativeRuntimeService.ts:174, :189).

   The test is whether the agent is a member of, or installed in, a pod outside the reach. One write has no pod: a thread comment on a post with no `podId` skips the pod check (agentsRuntime.ts:2283) and can be read across the instance. So every agent holding `commonly_post_thread_comment` holds an outward effect.
4. **Writing into a pod of the reach that does not keep it.** A pod in the reach still counts as outside in three cases. It is `publicRead` (Pod.ts:175), which is served without sign-in (server.ts:295). Any signed-in user can join it (`isDirectlyJoinable`, podListing.ts:93). Or it has a Telegram or Slack bridge: a bridge in mirror mode relays every agent post, and otherwise decides from the post's own text (`shouldEscalate`, connectorRelayPolicy.ts:33–36), so the agent that writes a post decides whether it leaves. In such a pod, every write in item 3 counts.
5. **A broker write that runs unattended.** A broker call parks when its definition is irreversible, or when its grant is `write-with-confirm` and the tool is not a read (toolBrokerService.ts:1136–1144). The mint refuses `write` only for hosted grants (grants.ts:336), so a GitHub grant can be minted `write`. Under such a grant, `github.close_issue` runs with no person, because it is the one GitHub write without `irreversible` (toolBrokerService.ts:364). `create_issue`, `comment_on_issue` and `merge_pull_request` declare it (:214, :337, :401). So an agent in the audience of a `write` GitHub grant holds an outward effect. A hosted grant does not: every hosted pin is `read`, and a write under `write-with-confirm` parks.
6. **Tools on the seat itself.** The server cannot list a seat's local tools, so it counts them by runtime and fails closed:
   - A seat the daemon runs (runtime kind `wrapper` or `local-cli`, or a runtime that names its adapter) holds none when the server can see that it is confined: it declares a `sandbox` block, and `grantBrokerRefusal` returns null for it (grantBrokerConfinement.ts:200). That function also returns null when no block is declared, leaving the seat to the daemon. This check cannot do that, because it needs to see the confinement. On claude, a public trust also denies Bash, Write, Edit and the web tools (adapters/claude.js:111–119), so only items 1–5 remain. A daemon-run seat with no sandbox block, or one the function refuses, holds local outward effects: a shell, the network, and any credentials on its host.
   - A `native` agent holds only the kernel tools its config declares (nativeRuntimeService.ts:128, :265), so items 1–4 cover it.
   - Every other runtime kind counts as holding, because the server has nothing to read: moltbot (openclaw's own tools run in the gateway, and dev agents carry a GitHub token), webhook, claude-code, hosted, internal and managed-agents.

The ruling's five names map onto these items:

- a merge is `github.merge_pull_request`, which always parks, or a seat-local `gh` (item 6);
- posting outside the pod is items 3 and 4;
- a DM is item 1;
- no kernel or broker tool sends email today, so email is item 6;
- a write to an external system is item 5, item 6, or a bridge (item 4).

**(b) Which sources count as outsider-writable.** A source is outsider-writable when someone outside the reach can write text its tools return. Each catalogue entry declares this and defaults to yes. An entry that says no must carry its reason, and the gate rules on it. Today every source is outsider-writable: the entries in `HOSTED_MCP_ENTRIES` (entries.ts:20), plus GitHub.

**(c) Where the check runs.** One function computes (a)'s list for a grant from current state. It runs at the mint and at call time, and not at attenuation.

- **At the mint** (`POST /api/grants`, grants.ts:298), after the existing checks and before the row is written. When the source is outsider-writable and the list is not empty, the mint refuses with `outward_effect_unaccepted` and returns the list, so the dialog can show who holds what. The same request, carrying an override (§12(d)) that names exactly that list, mints the grant.
- **At call time**, in `callTool` (toolBrokerService.ts:1092) and `executeApprovedToolCall` (:1282), next to the `assertGrantUsable` re-check both already run. These are the only two paths to a broker call (Vera, the TASK-212 row). The list is recomputed, and the call is refused with the same code when the list is not empty and no live override names it exactly. This is where change after the mint lands: an agent installed into the reach, a seat grant's seat installed into a new pod, a pod made public or bridged, a GitHub grant minted `write`. Reads are checked as well as writes, because a read is what brings outsider text into the reach. A call that waited for Approve is checked again, because the list can change while it waits.
- **Not at attenuation.** A child has its parent's reach, so its calls meet the call-time check.

A refused call writes its trail row like any refusal. It does not revoke the grant, which runs again once the list is empty or an override names it. Grants minted before the build are not exempt: their first call after it ships is refused until the owner records an override. That includes our own Linear grants.

**(d) The override.**

- **Who:** the connection's owner, the only person the mint accepts (grants.ts:306). They record it at the mint, or later from the Tools page for a grant whose calls are refused.
- **What it records**, on the root grant: who, when, the source (the connection and its entry id, or `github-app`), and the pairs it accepts. The pairs are exactly the list (c) computed at that moment, each `(agent, effect, where)`. The request must name the list the server computes, and any difference is refused. So an override cannot be blanket, and it cannot accept an effect before the effect exists.
- **Where it shows:** beside the grant on the Tools page, with its pairs, who and when.
- **When it covers:** a call runs only while the current list equals the accepted pairs.
- **How it ends.** An override that has ended never comes back.
  - Source side: revoking the grant (grants.ts:457–458) or removing its connection (`revokeConnectionGrants`, roomGrantService.ts:462) ends it with the grant.
  - Tool side: the first call that finds the list changed ends it, and that call is refused. The list has changed when a pair is gone (an agent uninstalled, a bridge removed, a `write` grant revoked) or a new one is present. A pair that comes back later, even the same one, needs a new override.
  - The owner can also withdraw it from the Tools page.

An override never touches part 1: the marker wraps every result either way.
